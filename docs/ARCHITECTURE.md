# Architecture

Qinari starts as a production-grade Next.js starter. This document explains
how the pieces fit so future decisions have something to lean on.

## Runtime layout

```
Browser ──> Next.js server (Node.js 24)
              ├── src/app/**          React Server Components, route handlers
              ├── src/components/**   UI building blocks
              └── src/lib/**          framework-free helpers
```

- **`src/app`** owns routing, layouts, metadata, and HTTP endpoints. Route
  handlers (e.g. `src/app/api/health/route.ts`) return JSON for machines;
  pages return HTML for people.
- **`src/components`** holds UI primitives composed by pages. Components are
  server components by default; a file only adds `"use client"` when it needs
  browser APIs or state.
- **`src/lib`** is framework-free. Code here must be importable from Node
  scripts and tests without pulling in React. Anything with reusable logic
  belongs here, with a unit test next to it.

## Data flow rules

1. Server components fetch data directly (database, filesystem, external
   APIs). No HTTP detour through the app's own API routes.
2. Route handlers exist for external consumers: health checks, webhooks,
   public JSON APIs.
3. Client components receive data as props, never fetch on mount when the
   server can fetch earlier.

## Tooling pipeline

The same gates run locally and in CI (`.github/workflows/ci.yml`), in this
order:

1. `tsc --noEmit` — types, including route types generated by Next.
2. `eslint` — correctness and React rules (flat config in
   `eslint.config.mjs`).
3. `vitest run` — unit tests (`src/lib/**`) and component tests
   (`src/components/**`) in jsdom.
4. `prettier --check` — formatting, with Tailwind class sorting.
5. `next build` — the only proof that the app actually builds.

A change is not done when it looks right; it is done when all five gates pass.

## Conventions

- Path alias `@/*` maps to `src/*` in both the app (`tsconfig.json`) and
  tests (`vitest.config.ts`).
- Prettier is the single formatting authority; do not fight it in review.
- Dependencies are updated by Dependabot weekly; dev dependencies are grouped
  so routine bumps arrive as one PR.
